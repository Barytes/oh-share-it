# hzhou9/TeamContext

分析对象是 [hzhou9/TeamContext](https://github.com/hzhou9/TeamContext)，版本 `0.1.0`。仓库创建于 2026-02-21，最近一次推送是 2026-03-06，公开页面上有 8 次提交、5 个 star、0 个 fork、0 个 issue。许可证是 Apache-2.0，实现语言是 Python，命令入口是 `tc`。

网上另有一个同名产品 [teamcontext.ai](https://teamcontext.ai/docs/)。那个产品用 npm 安装，通过 MCP、会话钩子和云端 API 记录团队里的 AI 编程活动。本文只讨论 hzhou9 这个 Git 仓库。

结论：TeamContext 把「同一个代码仓库里，这次编程会话做出的决定，要让下一位成员的编程 agent 读到」收成一套可以执行的命令。它减轻了痛点 1 里「整理成固定栏目、留下作者和时间、原始会话留在本机、避免大家改同一份大文档」这几件事。它没有从每个人电脑上的信息里，按当前任务检索出可以共享的那一部分。分析师之间互相冲突的指标定义、A 仓库和 B 仓库的上下文、以及「写下来之后模型仍然各写各的」，都留在流程外面。

## 分析时问的三个问题

这份分析按《创始人手册》Idea 阶段里「摸清竞争对手」的问法来写。手册要求对一个已经存在的做法做三件事：说明这个做法为什么实际上更好，说明有这些痛点的人为什么会选它，再说明我们自认为的差异为什么可能守不住。手册同时要求把现有做法还没接住的抱怨单独列出来。如果后来的方案正好对着这些抱怨，那是问题与方案匹配的证据；如果没对着，这一点本身也要记下来。

下面先写仓库里实际跑起来的行为，再按这三问做判断，然后逐条对照 `docs/customer-investigation/pain-points.md`。

## 仓库里实际发生的事

TeamContext 是装在开发者机器上的命令行工具。应用仓库保持独立。人在应用仓库里执行一次 `tc init`，之后的保存和同步交给该仓库里的编程 agent。`tc init` 会创建目录、写入配置和 OpenViking 的 lock、尝试把 [OpenViking](https://github.com/volcengine/OpenViking) 克隆到 `.tc/vendor/openviking`、立刻做一次同步，并生成给 agent 看的规则文件。

一个成员想把这次会话交出去时，对 agent 说 `save recent context to tc`。agent 必须自己从当前讨论里写出 `--intent` 和 `--decisions`，再执行 `tc agent save`。命令读取 Git 未提交的文件列表，把一段带固定栏目的 markdown 写进 `.viking/agfs/shared/changelog/`，并在 `.viking/agfs/shared/candidates/` 写一条标记为 `pending review` 的候选。人再自己执行 `git add`、`git commit`、`git push`。另一位成员 `git pull` 之后，对 agent 说 `sync latest context`，agent 执行 `tc sync --json`，把共享目录里的 markdown 扫进本机的 `.viking/index/index.txt`。会话开始时，bootstrap 要求 agent 先读 `decisions/`、`patterns/`、`runbooks/` 和这份索引；这三个目录为空时，agent 应报告还没有已批准的团队上下文，然后继续按代码本身工作。

共享目录的设计分成五类：`decisions/`、`patterns/`、`runbooks/`、`candidates/`、`changelog/`。`project_desc.md` 把前三类写成审查之后的事实，把 `candidates/` 写成待审查、默认不参与检索。当前代码里，`tc save` 和 `tc commit` 只写入 changelog 和 candidates。没有任何命令把候选移进 `decisions/`、`patterns/` 或 `runbooks/`。作者自己这个仓库跑过多次保存，共享区里有 8 篇 changelog 和 8 篇 candidate，`decisions/`、`patterns/`、`runbooks/` 下没有文件。bootstrap 让 agent 优先阅读的那三个目录，在这套工具的自我使用里是空的。

`project_desc.md` 还写了三件当前代码没有做成的事。它写 TeamContext 不调用 Git，代码里会 `git clone` OpenViking，并用 `git status` 决定哪些文件算这次变更。它写本地向量索引，`tc sync` 实际写出的 `index.txt` 是每个 markdown 的相对路径、修改时间和字节数；OpenViking 的索引入口若导入失败，命令仍返回成功，并改用这份清单。它写候选默认不进入检索，`tc sync` 会把 `shared/` 下全部 markdown 扫进索引，候选和 changelog 都在里面。

原始会话留在本机。`.gitignore` 忽略 `.tc/vendor/`、`.tc/state/`、`.viking/index/`、`.viking/agfs/sessions/`。会话语义先写入 `.tc/state/session_context.md`，这个文件不进入 Git。进入 Git 的是 changelog 和 candidate 里的那些栏目：意图变化、决定、决定状态、理由、影响范围、非代码讨论、验证结果、下一步、待办、未决问题。

保存前有三道闸。缺少意图或决定时，命令失败。bootstrap 一次涉及的文件数超过 1000 且没有 `--force-large-save` 时，命令失败。影响范围写成「没有应用代码变更」，但 Git 里又有非 TeamContext 文件变更时，命令失败。`tc verify-context` 检查最近的 changelog 是否带有意图、决定、理由、非代码讨论这四栏，并且内容不是字面量 `n/a`。

密钥扫描用三条正则，只检查即将写入的摘要文本，匹配 AWS access key、私钥块，以及 `api_key` / `token` / `secret` 后面跟着一长串字符。扫描发生在文件已经写到磁盘之后。发现匹配时，默认退出码是 2，文件仍留在共享目录里。作者仓库里的 `changelog/2026-02-20-joe-security.md` 和对应 candidate 已经提交，正文是 `api_key=1234567890123456`，这条文本符合第三条正则。

作者和时间写在文件头里，作者默认是本机操作系统用户名。文件名是「日期-用户-主题」。同一天、同一个用户、同一段意图 slug，后一次保存会覆盖前一个文件。不同用户会落到不同文件名上，Git 合并时不容易改到同一个文件。`.tc/agent/bootstrap_prompt.md` 和 `.tc/config.yaml` 会被提交，里面写的是绝对路径。作者仓库里的 bootstrap 指向 `/Users/joe/Documents/TeamContext/...`。新成员若直接使用这份已提交文件，读到的是另一台机器上的路径。

公开反馈只有 [Show HN: TeamContext](https://news.ycombinator.com/item?id=47103319) 下面的一条评论。评论者 eibrahim 承认多人同时对同一代码库下指令时，上下文会发散，也认为上下文放在 Git 里说得通。他问的是：成员之间的模型即使读了同一份共享上下文，仍会写出互相冲突的架构做法；共享上下文究竟减少了这种发散，还是只是把发散记录下来。帖子页面上没有作者的回复。仓库没有用户投诉可综合。没有投诉，反映的是还没有形成使用，不能当成满意。

## 这个做法为什么实际上更好

对「两个人用编程 agent 改同一个仓库，今天下午的决定明天还在」这件事，TeamContext 比痛点 1 里的 Google Drive `shared/` 文件夹更完整。

Drive 同步的是文件夹里的文件本身。两人同时写入同一份文档时会冲突，文件夹不记录谁在什么时候改了哪一段，一条内容属于共享还是私有，只看它躺在哪个目录。TeamContext 把一次交接写成新文件，文件头带日期和作者，历史留在 Git 里，可以用 pull request 看 diff。原始会话目录默认不提交。agent 被要求当场填意图、决定和理由，`tc verify-context` 会拒绝四栏缺失或写成 `n/a` 的 changelog。人不必自己设计文档结构，也不必把 `--intent` 手打进命令。

它也比「在 `CLAUDE.md` 里追加一句话」多了会话之间的增量。每一条 changelog 对应一次未提交变更和一段讨论，栏目里有影响范围和下一步。后来的 agent 至少有一批按时间排列的记录可以读，而不是只看到当前文件的最终样子。

这些优点都发生在一个已经存在的 Git 仓库内部，不需要新的服务器、账号和索引服务。`project_desc.md` 把远程共享索引明确写在 v0.1 范围之外。

## 有这些痛点的人为什么会选它

会选它的人，是已经用 Codex、Claude Code 或 Cursor 一起改同一个应用仓库的小组。他们的损失是重复解释架构约束、后加入的人看不到创始人做过的决定、并行分支各自维持一套说法。TeamContext 的 README 把这四件事写成自己要解决的问题。这个范围和痛点 1 里「编程 agent 需要公司里已经定过的内容」有重叠，和痛点 2、痛点 3 的重叠很小。

选择它的成本低。`pipx install` 之后，人只跑 `tc init`，保存和同步用两句自然语言交给 agent。交接物就是仓库里的 markdown，接收方继续用自己原来的编程工具。对一个不想引入知识库产品的两人小组，这套流程本周就能接上他们已有的 `git pull` / `git push`。

手册要求把这个选择看成真实威胁，而不是用 star 数把它打发掉。威胁在于：如果客户要办的事就是「这个仓库里的决定，另一位成员的 agent 明天读得到」，TeamContext 已经把这件事做成命令、目录和提交习惯。再做一个只覆盖同一件事的检索产品，客户有理由留在 Git 里。OpenViking 导入失败时，保存、changelog 和文件清单仍然能工作。有价值的部分是这套交接合同，引擎是否真的建成向量索引，不影响两人小组把决定交出去。

## 自认为的差异为什么可能守不住

如果差异被说成「我们会搜索，而他们只是把文件放进 Git」，这个差异在编程交接这个任务上守不住。TeamContext 的客户要的是交接之后读得到。`tc sync` 加上会话开头的必读目录，已经规定了 agent 读什么。客户不会为了一次架构决定再购买一套跨人检索。

如果差异被说成「我们有私有和共享的边界」，这个差异也要收窄。TeamContext 的边界是目录名加 `.gitignore`：会话和本机状态不提交，`shared/` 提交。这和 Drive 的 `shared/` 属于同一类规则，只是载体换成了 Git，并多了一次密钥正则。它没有阅读某人电脑上的笔记，再判断哪一段与当前任务有关、哪一段应当留下。筛选发生在保存的那一刻，由当时的 agent 决定把哪几句话写进栏目。

守得住的差异，要落在 TeamContext 自己的范围声明和代码都没有做的事情上。那就是：任务发生时，从多人的信息里取出这次要用、并且可以给对方看的部分；两套口径同时存在时标出分歧，并让 agent 知道该听哪一套；一个仓库里产生的结论，能被另一个仓库里的 agent 用到。下面按痛点说明它覆盖到哪一步。

## 对照痛点



### 痛点 1：本机信息交给队友和他的 agent

来源是 [Ask HN: How do you share agent context across a team?](https://news.ycombinator.com/item?id=48848840)。问题是自己电脑上的信息无法低摩擦地交给队友以及他的 agent。记录里对摩擦的理解是：自己先筛选，再传文件，再通知团队。现在的处理方式是用 Google Drive 同步一个 `shared/`，两个 agent 读写同一份公司内容，其余留在本机。同时写入会冲突，没有谁在何时改了什么的记录，共享还是私有只由文件夹名字决定。

同一条痛点下还有一条来自数据工程讨论的做法：每个季度都在重做同一份竞品分析，因为找不到上一份。他们的处理是每份文档开头写一行「这份文档是干什么的」，集中放在一处，之后用检索命令按这句话找到相关文档。

TeamContext 覆盖了这条痛点里「同仓库、编程会话、把决定交出去」的那一段。agent 代为整理栏目，人用 Git 完成传递。接收方 pull 之后执行同步，bootstrap 要求会话开始前读共享目录。作者、日期和 diff 解决了 Drive 文件夹缺少修改记录的问题。按人拆文件，降低了两人改同一份大文档的机会。会话目录不提交，本机讨论原文不会跟着仓库走。密钥正则对摘要里的明显密钥给出一次拦截。

它没有覆盖「电脑上那一锅信息」本身。`tc save` 的输入是当前仓库未提交的文件，加上 agent 从这次编程讨论里写出的栏目。定价笔记、客户笔记、竞品分析若本来就在仓库外，这条命令不会看见它们。人仍然要记得说保存，仍然要自己提交和推送，对方仍然要 pull 再让 agent 同步。工具不通知另一位成员。筛选仍然由保存时的 agent 完成，接收方的 agent 不会按自己手头的任务，回头到对方电脑上再选一次。

共享和私有的分界仍然是目录。`sessions/` 不提交，`shared/` 提交。一条半成品判断只要被写进 `--decisions`，就会进入准备提交的 changelog。扫描不阅读变更了的源代码，也不区分客户姓名、未定判断和私人内容。文件先落盘、命令后失败，所以拦截依赖人看见退出码之后不要提交。作者仓库里那条示例密钥说明，这道闸可以和提交结果同时存在。

「找不到上一份分析」只在分析已经被写进这个仓库的 changelog 时有一点帮助。栏目里有主题和意图，markdown 可以用文本搜索。`index.txt` 记录的是路径、修改时间和字节数，没有「这份文档是干什么的」这一行，也没有按这句话查询的命令。季度竞品分析若不在这个代码仓库的保存动作里，TeamContext 碰不到它。

`docs/product-design/team-context-problem.md` 把这件事定义成搜索：在团队所有人的信息中，取出当前任务需要、并且不涉及隐私的部分，放进 agent 的上下文。TeamContext 的检索发生在发布之后，对象只是已经写进 `shared/` 的文件。团队成员的 agent 知道的，是有人已经保存并推送过的栏目。还没保存的内容，对另一个 agent 来说不存在。

### 痛点 2：分析师 Skill 里的口径互相冲突

来源是 Joey Wu 的 Team Agent Skill。每个分析师有自己的 Skill，里面是他对表用途、字段含义和常用 join 的理解，用来让 agent 写出更准确的 query。多人之间会对指标定义不一致，或习惯用不同的表回答同一个业务问题，agent 因此生成有偏差的 query。现在的处理方式有两种：一份基础 Skill 再加个人定制；或者指定一个人收集、审核、合并，维护一份权威版本。

TeamContext 的目录草图接近第二种处理方式。`candidates/` 表示待审查，`decisions/` 表示审查后的事实，`tc verify-context` 要求决定和理由两栏有内容。一个团队可以约定：分析师把口径写进保存命令，负责人审查之后把文件放进 `decisions/`。

代码没有把这个约定做成步骤。`--kind` 可以填 `decision`、`pattern` 或 `runbook`，这个值只出现在候选文件的标题和文件名里，候选始终写在 `candidates/`。没有合并命令，没有「这两条对收入的定义不一致」的标记，没有个人 Skill 和基础 Skill 两层，也没有给 SQL agent 使用的口径选择。bootstrap 在权威目录为空时，指示 agent 报告没有已批准上下文，然后按代码继续。候选文件仍然被 `tc sync` 扫进索引。agent 若阅读 `index.txt`，会同时看见互相冲突、且都标记为待审查的条目，工具不告诉它该听哪一条。

因此，query 偏差这条后果没有被处理。TeamContext 不连接数据库，不保存表和字段的含义，也不比较两次查询结果。两位分析师各保存一次，得到两篇待审查 markdown。权威版本仍然要靠那位指定的人，用仓库以外的方式把文件挪进 `decisions/`。作者自己的仓库没有发生过这种挪动。

### 痛点 3：上下文停在单个仓库里

来源是 [How are you centralizing knowledge/context from AI agents?](https://www.reddit.com/r/dataengineering/comments/1t6ttuz/how_are_you_centralizing_knowledgecontext_from_ai/)。问题是 agent 只能把产物写回当前这次任务给定的目录或仓库，A 仓库和 B 仓库里已经产生的上下文互不相通。讨论里还记了两件相关的事。第一，把决定和规则写下来，并不保证模型不再生成另一套架构；这条意见来自 TeamContext 自己的 Show HN 评论。第二，记录某个决定，不等于当时的人想明白了动机和适用边界。例子是团队定了「收入不算退款」，把这句话写进 `CLAUDE.md` 之后 agent 可以查到原文，文件里仍然可以没有「为什么不算」以及「什么情况下这样算会错」。

讨论里已经出现的处理方式包括：中心化知识库、monorepo 或内部 wiki、单独的规则仓库加符号链接、专门仓库里的 `SKILL.md`、存放已确定事实的一处来源、Git 仓库内部分层上下文并由负责人定期把模块级规则升到顶层、用 MCP 区分仓库级、用户级和组织级。

TeamContext 是这些处理方式里「Git 仓库内部分层」的一种实现，而且层是加在单个应用仓库上的。`tc init` 在当前项目根目录创建 `.viking/`。仓库 A 和仓库 B 各有一份 `shared/`。v0.1 不托管远程索引，不同步原始会话，也没有 MCP、符号链接安装器和组织级知识库。A 里保存的部署约束，B 里的 agent 在自己的 `tc sync` 中看不到。

分层的晋升也没有操作界面。痛点记录里的做法是：顶层上下文全团队知道了才改，模块级上下文随代码提交，负责人定期看各分支哪里已经不一致、哪些规则应该升到顶层。TeamContext 有顶层目录的名字，没有随模块存放的上下文，没有跨分支比较，也没有把候选升到 `decisions/` 的命令。`project_desc.md` 把候选去重和冲突检测写在 v0.2。

Show HN 上的那个问题，在当前代码里仍然开着。preflight 提示词要求 agent 在上下文缺失或冲突时先提问。这是交给模型的一句指令。工具不比较两篇 candidate 里的架构说法，也不在第二次保存与第一次说法冲突时失败。共享上下文在这里的作用是把每次说法记下来，并希望下一个 agent 读到。它没有一道闸阻止模型在读过这些文件之后写出另一套做法。

理由栏目碰到了「写下来不等于想明白」的表面。`tc verify-context` 要求理由栏存在，且不是 `n/a`。栏里有一句完整的话就通过。它不检查这句话是否写了适用条件，也不检查什么情况下这个决定会错。agent 可以生成一句通顺的理由，验证命令会接受。痛点里的例子换成 TeamContext 之后，「收入不算退款」加上任意一句非 `n/a` 的理由，就能进入共享 changelog。

## 现有做法还没接住的抱怨

把上面三节收成客户仍会遇到的事，有六条。

1. 交接的材料是「这次仓库变更加上 agent 写出的栏目」，不是某人电脑上与当前任务有关、并且可以给对方看的那一部分。筛选、提交、通知仍然各算一次人为动作。
2. 私有和共享由目录名决定。半成品、客户信息和私人内容没有单独的判断。密钥正则覆盖三种明显格式，并且发生在文件已经写下之后。
3. 互相冲突的定义会并排留在 `candidates/`。工具不标出分歧，不选出权威版本，权威目录依赖人手工放置。作者仓库里这个目录没有被使用。
4. 每个应用仓库一份共享区。跨仓库的结论仍然要靠讨论里那些人已经在用的知识库、符号链接或单独的规则仓库。
5. 写进 Git 的决定，不阻止下一个模型生成另一套做法。公开评论问的就是这件事，仓库的后续提交没有加上冲突检测。
6. 理由栏保证那里有字。它不保证做决定的人想过适用边界和失败情况。旧文档能否被找到，取决于当初有没有人把它保存进这个仓库；索引本身不承载「这份文档是干什么的」。

这六条里，第 1、2、3 条和 `docs/product-design/team-context-problem.md` 的搜索定义直接相连：要在众人的信息里取出任务需要、不涉及隐私的部分，并让冲突的说法处于可以被看见的状态。第 4 条是痛点 3 的原问题，TeamContext 的范围声明把它留在外面。第 5、6 条说明，即使交接成功，读到原文也不等于 agent 会遵守，更不等于原文里含有可用的理由。

手册里的用法是：如果后来的方案对着这六条里的一条或多条，那是问题与方案匹配的证据；如果方案主要重复「把决定放进 Git、让 agent 在会话开头读一遍」，客户已经有 TeamContext 这条成本更低的路。
