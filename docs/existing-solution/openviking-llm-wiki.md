# OpenViking 的 LLM-Wiki

分析对象是 OpenViking 把已经导入的资料编译成团队 Wiki 的做法。公开叙述来自文章 [OpenViking × LLM-Wiki：让团队文档不再「各说各话」](https://mp.weixin.qq.com/s/rL5SQf7VQ9BV5wG9kaHGng)。可执行的规定来自 [Context Compilation](https://docs.openviking.ai/en/context-compilation/01-overview)、[LLM Wiki 示例](https://docs.openviking.ai/en/context-compilation/02-llm-wiki)、[`llm-wiki/SKILL.md`](https://github.com/volcengine/OpenViking/blob/skills/llm-wiki/SKILL.md)（`skills` 分支，blob `b66058ab`），以及资源、多租户和 ACL 文档。本文讨论 OpenViking 自己的编译。`docs/existing-solution/TeamContext.md` 里的命令行工具把 OpenViking 当作本地依赖，那是另一套做法。

结论：这套做法把「飞书、本地文件和代码仓库里已经有文档，口径互相冲突，agent 能引用却判断不了哪一条适用于眼前这个客户」收成导入、编译、查阅和检索四步。它覆盖了痛点 2 里「把冲突留下来源」、痛点 3 里「多个仓库进同一处再检索」、痛点 1 里「共享之后队友和他的 agent 读同一份整理结果」。检索对象是已经放进 `viking://` 的资料。任务发生时，从每个人电脑上尚未导入的信息里取出这次要用、并且可以给对方看的部分，留在这四步外面。

## 分析时问的三个问题

这份分析按《创始人手册》Idea 阶段里「摸清竞争对手」的问法来写：这个做法为什么实际上更好，有这些痛点的人为什么会选它，自认为的差异为什么可能守不住。现有做法还没接住的抱怨单独列出。对着这些抱怨的方案，是问题与方案匹配的证据；主要重复「把已有文档编成一份带导航和来源的 Wiki，让每个 agent 去读」的方案，客户已经有这条路。

下面先写文章里的场景，再写文档和 Skill 规定的行为，然后按三问做判断，并逐条对照 `docs/customer-investigation/pain-points.md`。

## 文章里的那通电话

文章用一通赔付电话说明缺口。客户问没有保价的货出了问题怎么赔。老王说按 1 倍运费。小李翻出的产品文档写着 3 倍基本运费、最高 1000 元。售后说要分产品再查。三份都是正式材料。办公智能体检索了团队知识库，给出多种带引用的口径，并说明根据当前信息无法准确回复，要求先确认客户采购的服务类型，再查对应的计费标准。

文章把这个缺口写成：文档和知识库已经有了，检索也有了，客户、产品、规则和流程之间的适用关系还没有整理成以后能沿用的页面。

文章引用 Andrej Karpathy 在 2026 年 4 月提出的 LLM-Wiki。原始资料和使用者之间增加一层由模型维护的、持久的 Markdown Wiki。新资料进入后，更新实体页、概念页和对比页，补充交叉引用，并标出新旧材料之间的矛盾。文章设想的查阅顺序是：先读客户页，确认采购了什么服务；再读产品页，确认产品、线路和服务范围；再读计费与赔付页，找到当前生效的标准、适用条件和例外。

## 导入、编译、查阅和检索

导入先于编译。`ov add-resource` 接受本地目录、上传的本地文件、HTTP(S) 和 Git URL。Git 协议导入遵循 `.gitignore`，并过滤 `.git`、`node_modules` 等目录。飞书文档、表格、多维表格和云盘可以用 URL 导入；默认使用应用凭证，用户 token 放在 `args.feishu_access_token`。远程来源设置 `watch_interval`（单位是分钟）之后，按这个间隔重新导入。通过临时文件上传的本地内容是一次性快照，不能创建监控任务。目标 URI 已经存在时，这次导入覆盖该目标。

导入完成之后，这些资料已经可以检索。目录带有 L0 摘要和 L1 概述，正文是 L2。agent 先读摘要判断相关性，再打开正文。语义搜索可以限制在一个目录里。文章把这一步写成编译之前就能交给 Codex、TRAE 等使用。官方文档把分层读取和目录级检索写成 OpenViking 的基本能力，和 Wiki 编译是先后两件事。

编译由 `ov compile` 发起。必填三项是来源 `--from`、目标 `--to`、规则 `--skill`，可选补充说明 `--instruction`。命令立刻返回 `cmp_...` 任务号，用 `ov task status` 查看进度。执行者是启用了 Bot 的 OpenViking 服务（`openviking-server --with-bot`）。文章里的控制台路径还要求开通火山方舟 Managed Agents，并配置推理接入点。开源服务按 AGPLv3 自行部署，不需要激活密钥；火山引擎另有托管版和在客户云账号里部署的版本。VikingBot 以调用者的身份读取来源，在单独的 agent 循环里按 Skill 写页面。产物形态由这次指定的 Skill 决定。同一批来源换日报、知识蒸馏或知识图谱 Skill，写出来的是另一种目录。

官方 `llm-wiki` Skill 规定了编译合同时要遵守的事。原始来源保持只读。知识写进持久的 Markdown。新证据并入已有页面。页面之间保留交叉引用，来源互相矛盾时把矛盾和出处一起留下，并区分错误、时间变化、版本、视角和适用范围。根目录的 `index.md` 做导航，列出每一页和一句检索摘要。页面类型默认是 `entity` 和 `concept`。`method`、`comparison`、`analysis` 要满足更严的用途测试才使用。`summary` 只有 `--instruction` 明确要求时才写，避免按原始文件再堆一层摘要。每条实质论断旁边要有来源 URI 或路径。Skill 禁止编造 URI、数字和因果关系，禁止用一般知识填上来源里没有的事实。更新已有页面时先读全文，保留人补上的、新证据没有推翻的内容。

这些要求写在 Skill 正文里，由执行编译的模型在结束前自行核对。文档里没有另一道独立程序：页面漏了适用地区、没有标出矛盾，或数字和来源对不上时，任务仍然可以完成。

Skill 默认装进当前用户自己的 skill 命名空间。加上 `-p viking://agent/skills` 才放到团队共用的位置。文章要求业务自己的 Skill 写清四件事：给谁用、按什么方式组织、哪些事实和条件必须保留、完成后如何检查。赔付场景里的产品、地区、版本、例外，以及「客户 → 服务 → 产品 → 规则」，写在这份额外 Skill 或 `--instruction` 里。官方模板的页面按检索用途划分，模板正文没有这条业务链。

编译结果放在 `--to`。有读权限的人用控制台或 `ov read` 打开 `index.md`，再进入单页。文章写了页面右上角可以编辑并保存，下一位同事打开的是保存之后的内容。下一次编译被 Skill 要求保留这些人工修改。

检索靠另一份 Skill。文章建议写清四件事：遇到客户服务、适用范围、计费或赔付时查阅团队 Wiki；先用导航或检索定位，再读正文；沿客户、服务、产品、规则核对地区、时间和例外，必要时回看来源；给出结论、适用条件和来源，依据不足或口径冲突时说明情况。Codex、Claude Code、Cursor 等通过各自的记忆插件或 MCP 连接同一套服务。文章里的 Codex 安装会审批四个 hook：`SessionStart`、`UserPromptSubmit`、`Stop`、`PreCompact`。这些 hook 做记忆召回和会话捕获。指定去读 `viking://resources/.../wiki/index.md` 是另一步。

共享和私有按 URI 划分。`viking://resources/...` 是账户内的共享资源。`viking://user/{user_id}/` 下面的资源、记忆、技能和会话默认只属于该用户。要给同事看，把资源移动到有写入权的共享目录。ACL 默认关闭；关闭时，共享资源按原有命名空间规则可见。ACL 打开之后，共享根目录固定是账户内全员 `manage`，直到某个目录被设成 `restricted` 并单独授权。编译读取调用者已经能读的 `--from`，写入调用者能写的 `--to`。它不读取账户里其他用户的用户目录。

## 这个做法为什么实际上更好

对「正式文档散落在飞书、本地和仓库里，三份都像对的，agent 把三份都引出来」这件事，OpenViking 的编译比痛点 1 里的 Google Drive `shared/` 多了整理和以后沿用的页面。

Drive 同步的是文件本身。口径冲突留在三份原文里，后来的人自己判断哪一份适用于这个客户。`ov compile` 把调用者指定的来源收成一组互相链接的页面，`index.md` 列出每页的检索用途。Skill 要求矛盾留下来源，并要求更新时改已有页面。人可以在页面上补上编译漏掉的适用地区，下一次编译要保留这段内容。多个 Git 仓库和飞书文档可以进入同一个 `viking://resources` 树，再编译进同一个 `--to`。接收方的 agent 读这个 URI，不必先拉取某一个应用仓库。

分层读取在导入之后就可用。agent 先看目录摘要，再打开正文，也可以把搜索限制在 Wiki 那个目录。

这些步骤有命令、目录和 Skill 文件。开源服务可以自己部署，火山引擎也提供托管。客户要办的事如果是「把已经集中的资料编成一份人和 agent 都能打开的 Wiki」，可以接到他们已有的飞书和 GitHub。

## 有这些痛点的人为什么会选它

会选它的人，文档已经在飞书、网盘或代码仓库里，办公 agent 也已经能检索，检索结果是多条互相冲突的引用。文章里的新人答不了那通赔付电话，就是这个损失。OpenViking 把知识、记忆和技能放在同一套 `viking://` 文件系统里，`ov compile` 负责把指定原料写成可以反复打开的页面。

已经在跑 OpenViking 的团队，增加的动作是一次 `add-skill`、一次 `compile`，以及一份告诉 agent 先读 Wiki 的检索 Skill。还没部署的团队，要先有嵌入模型和视觉语言模型，自己启动服务或开通托管，再完成飞书授权和 agent 的 hook。托管版省掉自建服务器，账户、API Key 和模型接入点仍然要配置。

这是真实威胁。客户要办的事如果是「多处已有文档编成一份带导航和来源的 Wiki，每个成员的 agent 检索同一份」，OpenViking 已经把导入、定时更新、编译、页面编辑、目录级检索和各家 agent 的接入做成产品。再做一个只覆盖同一件事的 Wiki 编译器，客户有理由留在这套 URI 里。某次赔付材料有没有被写成带适用地区的页面，不影响他们先把文档导入，并让 agent 按目录去读。

## 自认为的差异为什么可能守不住

`docs/product-design/team-context-problem.md` 把要做的事定义成搜索：在团队所有人的信息中，取出当前任务需要、并且不涉及隐私的部分，放进 agent 的上下文，并让团队和成员的 agent 知道这些信息存在。

差异如果落在「把散落文档编成互相链接、标出矛盾的 Wiki」，这个差异守不住。官方 Skill 已经把实体页、概念页、交叉引用、矛盾与来源、`index.md` 写成编译时要遵守的合同。客户要的适用关系，可以写进 `--instruction` 或自定义 Skill。

差异如果落在「私有和共享有边界」，能守住的范围要收到查询发生的时刻。OpenViking 的边界在导入和移动的时刻：共享目录对账户内默认可读，用户目录默认不共享，ACL 打开后按目录授权。回答这通电话时，编译不会去读每位同事电脑上还没导入的文件，再决定哪一段与赔付有关、哪一段应当留下。

差异如果落在「agent 知道该听哪一条口径」，能守住的范围同样要收窄。Skill 要求把矛盾留在页面上。文章里的检索 Skill 要求口径冲突时说明冲突。两者都是交给模型的指令。两条赔付标准同时留在来源里时，没有一道闸选出当前客户适用的那一条，也没有在模型仍然报出一个数字时让这次回答失败。客户、服务和产品之间的链接，依赖这些事实已经写在来源里，并且这次编译把它们写成了页面。

守得住的差异，落在这套产品的导入范围和页面目录没有覆盖的事情上。任务发生时，从多人尚未放入 `viking://` 的信息里取出这次要用、并且可以给对方看的部分。两条口径都留下之后，标出眼前这个客户该听哪一套。团队所知道的范围，包括还没有人导入的信息，而不只是 `index.md` 里已经编出来的页面。

## 对照痛点

### 痛点 1：本机信息交给队友和他的 agent

来源是 [Ask HN: How do you share agent context across a team?](https://news.ycombinator.com/item?id=48848840)。自己电脑上的信息要先筛选，再传文件，再通知团队。现在的处理方式是用 Google Drive 同步一个 `shared/`，两个 agent 读写同一份公司内容，其余留在本机。同时写入会冲突，没有谁在何时改了什么的记录，共享还是私有只由文件夹名字决定。

同一条痛点下还有一种做法：每份文档开头写一行「这份文档是干什么的」，集中放在一处，之后用检索命令按这句话找到相关文档。他们用这个办法避免每个季度重做同一份竞品分析。

OpenViking 覆盖了「选定的文件进入一处、整理成页面、队友和他的 agent 按 URI 去读」这一段。本地文件用上传或 `ov add-resource` 放进 `viking://resources`。飞书和 Git 可以按分钟级间隔重新导入。编译之后，`index.md` 的每一行是页面路径加一句检索摘要，页面开头的 `description` 是一句检索用途。这和「这份文档是干什么的」同一类入口。接收方的 agent 通过 MCP 或记忆插件访问同一个服务；检索 Skill 再规定先读 Wiki。

筛选仍然发生在导入之前。人选择本地目录、授权飞书、填写 `--from`。本地上传是一次性快照，电脑上后来新增的文件不会自动出现。工具不通知另一位成员。另一位成员的 agent 要已经接上这个服务，并且被指向 Wiki，才读得到这次编译。

共享和私有仍然由目录决定。放进 `viking://resources` 的内容，在 ACL 关闭时按账户内的共享规则可见。`include` 和 `exclude` 按文件名模式过滤，Git 导入再遵守 `.gitignore`。这些规则不阅读正文，也不区分客户姓名、未定判断和私人笔记。用户自己的记忆留在 `viking://user/{user_id}/`。文章推荐安装的 hook 会把该用户的记忆摘要召回进会话，这一路上下文和团队 Wiki 分开。

上一份竞品分析只有已经被导入时，才能靠摘要、`description` 和 `ov find` 再找到。没有人导入的那一份，不在这棵资源树里。

`docs/product-design/team-context-problem.md` 要求的搜索，发生在众人的信息之上，并且在进入上下文之前去掉不该共享的部分。OpenViking 的检索发生在导入之后，对象是调用者有权阅读的 `viking://`。还没导入的内容，对另一个 agent 来说不存在。

### 痛点 2：分析师 Skill 里的口径互相冲突

来源是 Joey Wu 的 Team Agent Skill。每个分析师有自己的 Skill，里面是他对表用途、字段含义和常用 join 的理解。多人之间会对指标定义不一致，或习惯用不同的表回答同一个业务问题，agent 因此生成有偏差的 query。现在的处理方式有两种：一份基础 Skill 再加个人定制；或者指定一个人收集、审核、合并，维护一份权威版本。

OpenViking 可以接收这些 Skill 文本，前提是有人把它们放进 `--from`。官方模板允许用 `comparison` 页把多个对象放在同一组维度上比较。来源互相矛盾时，Skill 要求保留矛盾、带来源，并区分版本和适用范围。文章里的检索 Skill 要求此时说明冲突。个人 Skill 默认在用户自己的命名空间里；放到 `viking://agent/skills` 才成为团队共用的那一份。

代码和文档里没有合并命令，没有「这两条对收入的定义不一致」的自动标记，也没有指定负责人之后把某一条升成权威版本的步骤。权威版本要靠人编辑页面，或在 `--instruction` 里写明以哪一份为准。Skill 同时要求保留矛盾、禁止用一般知识补上缺失的判断，所以默认结果是两套口径一起留下。OpenViking 不连接数据库，不保存表和字段的含义，也不比较两次查询结果。query 偏差仍然要靠读到这些页面的 agent 自己停下来。两份互相冲突的分析师 Skill 若没有被放进同一次 `--from`，编译看不到它们。

### 痛点 3：上下文停在单个仓库里

来源是 [How are you centralizing knowledge/context from AI agents?](https://www.reddit.com/r/dataengineering/comments/1t6ttuz/how_are_you_centralizing_knowledgecontext_from_ai/)。agent 只能把产物写回当前这次任务给定的目录或仓库，A 仓库和 B 仓库里已经产生的上下文互不相通。讨论里还记了两件事。第一，把决定和规则写下来，并不保证模型不再生成另一套架构。第二，记录某个决定，不等于当时的人想明白了动机和适用边界。例子是团队定了「收入不算退款」，把这句话写进 `CLAUDE.md` 之后 agent 可以查到原文，文件里仍然可以没有「为什么不算」以及「什么情况下这样算会错」。

讨论里已经出现的处理方式包括：中心化知识库、内部 wiki、单独的规则仓库、存放已确定事实的一处来源，以及用 MCP 区分仓库级、用户级和组织级。

OpenViking 实现的是其中的中心化知识库。仓库 A 和仓库 B 的地址都可以 `add-resource` 到同一个 `viking://resources`，再作为多个 `--from` 进入同一次编译。飞书文档和本地文件可以进同一棵树。账户是团队边界，用户目录是个人边界，ACL 是共享目录上的进一步授权。这比加在单个应用仓库里的一层目录更接近痛点 3 的原问题。

会话里新产生的结论不会自动进入这份 Wiki。记忆插件把会话捕获进该用户的记忆。共享 Wiki 只在有人把这些材料放进 `--from` 并再次执行 `compile` 时更新。日报 Skill 把材料按日期写成另一组页面，那是另一次编译，目标目录也另选。

写下来的决定仍然不阻止下一个模型生成另一套做法。检索 Skill 是一段要模型遵守的说明。工具不比较 agent 这次的输出和 Wiki 里已有的说法，也不在两者冲突时让回答失败。

适用边界碰到了 Skill 的表面要求。概念页可以写约束和取舍，方法页要写失败情况，分析页要写不确定。Skill 同时写了「只放用得上的内容」，空的约束不会变成一个必填栏目。页面里有一句「收入不算退款」加上来源链接，就可以通过模型自己的结束检查。它不检查做决定的人是否想过什么情况下这样算会错。

### 痛点 4：agent 写下的团队 wiki 会把错误留下来

来源是 [Show HN: A Karpathy-style LLM wiki](https://news.ycombinator.com/item?id=47899844)，做法记录在 `docs/existing-solution/team-wiki.md`。放进去的事实是错的，整理出来的摘要也是错的。没有人看过的条目坏得最快。错误条目会被别的 agent 引用。模型可以一直写，人不再读。人自己不把决定讲清楚，只把会议记录交给模型，后面的提升也留不住对的内容。

OpenViking 的 `llm-wiki` 正是由模型把来源写成团队可读的 Wiki。Skill 用来压住其中几件事：禁止编造，论断旁边带来源，默认不按原始文件各写一篇摘要，更新时保留人改过的内容，结束前按一份清单自查。编译完成时，页面直接出现在 `--to`。有读权限的同事和接上检索的 agent 随后就能打开。文档里没有「人批准之后才提升」的目录或命令。

来源里的错误会带着引用进入页面。Skill 写明不能用来源以外的知识判断对错；重要论断没有来源支持时，应当缩小或跳过这一页。一份看起来正式、内容错误的赔付细则，仍然是合格来源。每日另跑一遍、专门找出过期和矛盾的任务，在编译文档里没有对应命令。矛盾处理发生在这一次编译阅读来源的时候。

人没有把决定讲清楚时，Skill 要求把未知留在页面上，禁止用一般知识补成结论。会议记录里如果本来就没有「定了什么」，编译不会从记录之外变出这个决定。文章的电话场景假定三份正式材料已经存在，所以这一步在那个场景里被跳过了。材料存在，只说明有字可以引用，不说明其中一份是当前客户该用的标准。

## 现有做法还没接住的抱怨

把上面四节收成客户仍会遇到的事，有六条。

1. 进入检索的材料，是有人已经导入到 `viking://` 的那一部分。任务发生时，从每人电脑上尚未导入的信息里再选「这次要用、并且可以给对方看」的部分，不在导入和编译里。筛选发生在选择目录、授权飞书和填写 `--from` 的时候。
2. 私有和共享由 URI 和可选 ACL 决定，决定发生在放入共享目录之前。用户记忆默认留在用户空间。文章里的 agent 安装会把该用户自己的记忆摘要召回进会话，这一路和团队 Wiki 同时出现在上下文里。
3. 矛盾被要求留下来源。眼前这个客户该用 1 倍还是 3 倍，依赖来源里已经写了采购的服务类型，并且检索 Skill 要求模型沿客户、产品、规则去核对。官方模板没有这条链。模型仍然直接报出一个数字时，没有命令会失败。
4. 编译写完就落在团队可读的 `--to`。没有人看过才提升的队列。来源里的错误会带着引用进入页面。Skill 的自查不判断来源对错。
5. 原始资料在编译之后仍然留在资源树里，文章也写明导入之后就可以交给 agent 检索。检索范围若不是 Wiki 目录，agent 仍会读到那三份互相冲突的原文。
6. `index.md` 列出的是已经编译的页面。还没有人导入的笔记、还没有写进来源的决定，不出现在这份导航里。团队因此知道的是 Wiki 里有什么。成员的 agent 知道的是它被允许检索的 URI 里有什么。

这六条里，第 1、2、6 条和 `docs/product-design/team-context-problem.md` 的搜索定义直接相连：要在众人的信息里取出任务需要、不涉及隐私的部分，并让团队和 agent 知道这些信息存在，包括尚未被整理进 Wiki 的那一部分。第 3 条是文章自己的赔付场景里还没被命令保证的那一步。第 4 条是痛点 4 的原问题，编译把它留在模型自查和事后人工编辑上。第 5 条说明，Wiki 和原始文档会同时可被检索，适用关系要靠检索范围和检索 Skill 才生效。

手册里的用法是：后来的方案对着这六条里的一条或多条，那是问题与方案匹配的证据。方案主要重复「把已导入的文档编成带导航和来源的 Wiki，让 agent 在会话里去读」，客户已经有 OpenViking 的 `ov compile` 和官方 `llm-wiki` Skill。

## 证据边界

以上结论来自 2026-09-26 读到的微信文章、`skills` 分支上的 `llm-wiki/SKILL.md`、编译概览、LLM Wiki 示例、资源 API、多租户文档和 ACL 文档。没有在本机执行 `ov compile`，没有用赔付材料跑过一次编译，也没有公开的使用者访谈。

文章里的电话、三个答案，以及下一次可以当场回答，是产品叙述，不是一次公开的运行记录。火山方舟 Managed Agents 那篇前置文档没有取到正文，控制台编译的前置条件以文章中的句子为准。开源路径以编译文档中的 VikingBot 为准。

判断它是否接住痛点时，以 Skill 要求模型做的事，以及文档里的 URI、权限和导入规则为准。Skill 写了「保留矛盾」「保留人工修改」，等于模型被要求这样做。一次真实编译是否写出了适用地区、是否把 1 倍和 3 倍标成未解决的冲突，要看那次任务的页面，本文没有这份页面。
