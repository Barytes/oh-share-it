Joey Wu问：
大家好，想请教下 如何在多人协作中规模化管理 Agent Skill 的知识库？
背景： 我们团队建了一个 Agent Skill 来辅助 SQL 查询。因为公司数据库很多，且 schema 和 field level 都缺乏文档，所以我们用 YAML 文件让分析师把自己对数据库的理解（表的用途、字段含义、常用 join 逻辑等）补充进去，供 AI 生成更准确的 query。
核心矛盾： 1-2 人协作时问题不大，沟通一下就能对齐。但一旦扩展到更多人，不同分析师对同一张表、同一个字段的理解和使用习惯会产生冲突，比如对某个指标的定义不同，或者习惯用不同的表来回答同一个业务问题。这些分歧直接导致 Agent 输出的 query 出现偏差。
我们考虑的两种方案：
方案 A：基础版 + 个人定制 维护一套大家公认的基础 skill/YAML，涵盖核心表和通用定义；其余部分每个人自行 customize。
优点：推进快，降低协作摩擦
缺点：知识仍然散落在各个分析师手里，无法沉淀为系统性的团队知识资产
方案 B：中心化审核管理 指定专人负责收集、审核、合并各分析师的知识贡献，统一维护一份权威版本。
优点：能形成系统性知识，保证一致性
缺点：审核和沟通成本极高，本身就违背了做这个工具的初衷（提效）
约束条件： 我们知道最根本的解法是从数据库文档本身下手，但现阶段无法撬动工程团队去补全文档，只能在现有条件下找最优解。
想请教的问题： 在这两种方案之间，大家会怎么选？或者有没有第三种方案，能在不投入过多人力的前提下，逐步把分散的 domain knowledge 沉淀成系统性的团队知识？

我答：
hi，我最近遇到的场景有类似之处，希望我的思考能提供一些帮助。也希望听听其他人的想法。
背景：我在给我们课题组搭建一个公共知识库，希望把所有成员的研究经验积累起来沉淀成资产，让未来的所有人都可受益。
问题1：如何高效地积累知识并分发给每个人？
类比1：在你的场景里，就是如何把各个分析师手里的知识收集起来，沉淀成团队资产。
尝试与失败：直接把课题组所有成员的研究笔记收集到课题组的公共服务器，形成一个大知识库，并配置一个公共的AI Agent检索它，来回答每个人的问题。但问题在于，材料太多，AI Agent的检索效率低下，回答质量差，token消耗大。
解决方案1：设计一个两层架构的知识库：每个成员有一个个人知识库，在服务器上放一个公共知识库。个人库的内容定期上传到公共库聚合，聚合后的公共库内容再下发到个人库。
问题2：如何设计公共库的聚合策略，以提高Agent的检索效率，同时保留回答的启发性？
类比2.1：在我的场景里，是希望agent的回答让用户觉得有启发性。在你的场景里，就等同于每个人得到的query更准确地符合自己实际想要查询的内容？
洞察2.1：知识库内的数据可以分为两类。一类是user agnostic knowledge，如领域内的基础知识、通用方法等；另一类是user specific knowledge，如个人的猜想、理解、尝试、判断等。（这个洞察来源于开源了一个让AI Agent自我进化的AI harness 工具#comment 的作者，可以看我们在帖子内的讨论）
洞察2.2：user agnostic knowledge需要尽量聚合，以提升Agent的检索效率。user specific knowledge不应当聚合，一方面是不应当干扰每个人自己的理解判断，仅把他人的理解作为一个参考，另一方面是保留多样性，保留新见解诞生的空间。对于一个问题，Agent应当以user agnostic knowledge作为基础的context，但是如何筛选不同人的user specific knowledge进入context，不同用户需要不同的策略。
类比2.2：类比到你的场景，数据库的核心表和通用定义属于user agnostic knowledge，而每个分析师的理解和使用习惯属于user specific knowledge。对于同一个数据库，应当维护一份公认的基础skill/YAML，但是收集起来的多个分析师的理解如何使用，需要根据提问的那个人的偏好和习惯设计专属的策略。
问题3：针对使用Agent的不同用户，如何设计使用aggregated user specific knowledge的策略？
猜想：这个问题我也没想到解决方案。目前有些猜想：1）借鉴鸭哥的为什么AI只会说正确的废话，以及怎么把它逼出舒适区  ，从多个user的specific knowledge里提炼出patterns-axioms，然后用axioms来指导Agent的回答。但是这样又消灭掉了user specific knowledge中本身包含的多样性——例如可能分析师A的理解在场景A里超级有效，分析师B的理解在场景B里超级有效。2）设计一个动态路由机制，例如给每个人的specific knowledge设计一个权重，然后按照不同场景的提问动态调整权重。这里面又有很多设计的空间。最近了解到的想法是，可以把每个用户跟Agent交互的trace收集起来作为数据，这些trace就可以用来设计使用aggregated user specific knowledge的策略。
总结：我的理解是 1）公共库-个人库的双层架构能低成本地收集个人的domain knowledge沉淀成团队资产，并将团队资产分发给个人；2）个人的domain knowledge如何沉淀成有效的团队资产，需要设计聚合机制；3）团队资产如何对个人有用，需要针对个人设计有效的使用策略。
