大家好，能听见我说话吗？谢谢你们过来。房间里居然有人，这很好。

我是 Jean-Denis，现在是 Town 的 CTO。今天不讲 Town 本身，如果你们想了解，可以去 town.com 看。我在 Plaid 做了七年 CTO，再之前在 Dropbox，再之前给对冲基金写软件。我现在做的是给普通人用的助手型 agent，对象不是工程师，而是美国和全世界的普通人。

我们最近在做的一类系统，是 agent 和其他 agent 一起工作，也就是 agent-to-agent。核心想法是：如果 agent 能够互相协作，替人把事情做完，就会出现很大的网络效应。现实世界里，大多数人本来就是和其他人一起工作的，协作的人越多越好。但我并不认为 agent-to-agent 作为一个概念很说得通。所以我想把整场演讲重新表述成一个搜索问题。

## 大多数 LLM 系统都是搜索问题

我认为，大多数 LLM 系统本质上都是搜索问题。你要做的事情是：在把结果返回给用户之前，或者在发起一次工具调用之前，确保当时的上下文窗口里已经有正确的信息。只要把正确的信息放进上下文窗口，再凭借当时 LLM 的智能程度，你就能得到当时能得到的最好结果。

四年前，人类会手工把信息放进上下文窗口。两三年前，很多人在做检索增强生成：做一个搜索工具，让它跨越多个系统把数据取回来。后来大家发现这种方式扩展不好，也有各种问题。现在大家都在做 agentic search：给 agent 很多工具，让它在全部可得内容里自己搜索；希望它在发起工具调用之前，已经拿到恰好正确的内容，从而做出正确的工具调用，再把正确的信息返回给用户。

在这套图景里，真正重要的不是有多少个人、多少个 agent 人格。真正重要的是那一次关键的 LLM 调用：那一次调用的上下文必须是对的。你要工程化的就是这个时刻。

## 理想状态是一个能看到全部信息的 agent

这和 agent-to-agent 有什么关系？请想象下面这个世界。世界上并没有很多能做事的 agent，只有一个 agent。它只有一个上下文窗口，但它能访问宇宙里的全部信息：任何一个人的邮件、任何一家公司的信息、任何一个政府的信息。这些信息就在它的上下文窗口里。然后你让它做事。你给它系统提示和这些数据。接下来发生的事情是：它会给出最好的结果。

那其实就是一个多智能体世界。它只是一个能访问全世界信息的 agent。这是自然状态，也是理想状态。

这个状态有一个问题。经济学里有科斯定理：即使是人类，只要各方都拥有正确的信息，并且不存在交易成本，协商就能得到经济上的理想结果。LLM 这边也是同一件事。我们不能把全世界的联系人和记录都提供给 LLM。即使上下文窗口无限长，隐私和安全也不允许这样做。我们是人。我不让你看我的邮件，所以别人不可能拥有一个我愿意让它随时查看我邮件的通用 agent。可是，如果这样的 agent 存在，它会非常强。

因此，评价一个多智能体系统的标准是：它在多大程度上逼近这个理想状态。如果它能把一个拥有全世界数据的完美系统会用到的那些数据，放进自己那一次关键调用的上下文窗口，它就能得到最优结果。这就是你需要努力去做的事。

下面讲五种策略。不同公司用这些策略，试图在信息仍然分属于不同私有范围的前提下，把正确的数据送进那一次 LLM 调用。这里的私有范围，我称为信息孤岛：信息只存在于某个人或某个团队的私有系统里，其他人或 agent 默认无法访问。

## 策略一：在信任边界内近似获得全部访问权限

第一种策略，是在一条信任边界之内，让一个 agent 近似拥有全部访问权限。我和我的妻子共用一个 agent。这个 agent 能访问我的邮件，也能访问她的邮件，包括我们结婚之前的邮件。她不会拿结婚前的邮件来问我的 agent，但她会问：我有没有给孩子安排某件事，或者我有没有跟进某个第三方事项。我们的 agent 能同时访问两个人的系统，这一点非常好。

放到工作场景里，这可能是一个人力资源团队的 agent。它能访问全部人力资源系统，访问权限相当于人力资源团队里权限最低的那名员工。人力资源团队的所有人都可以向这个 agent 提问，结果会相当不错。

这种做法现在很流行。信息技术团队和安全团队喜欢它，因为它和现有 SaaS 的安全模型一样，所以容易落地。它有一个根本问题。我每天早上醒来几乎只想这件事：随着时间推移，这个系统是否会自然地减少对人类的依赖？随着模型变强，这种做法是否会一起变强？对这两种问题，这种做法的答案都是：不会。你仍然需要人类去思考全部数据；你也不会因为模型变强，就自动打通原来的信息孤岛。你只是因为某个人做了一个决定，又造出了一座新的信息孤岛。

如果你把这种做法当成建设更好 AI 的长期路线，未来几年你会落后。这没关系，你的落后是我的机会。这句话有点过分，抱歉。我认为它是一种合理的现在做法，不是一种合理的终局做法。

## 策略二：在能力与隐私之间做不同取舍的工具

第二种策略更巧妙：你去设计一类工具，让它们在能力与隐私之间做出和“直接打开全部原始数据”不同的取舍。

举一个用例。我想问我的 agent：我们公司里有没有人认识 Acme 公司财务团队的人？如果没有任何信息孤岛，做法就是：给我公司里每个人的 Gmail 访问权限，我去看谁和 Acme 的人通过邮件；再去 Google 或 LinkedIn 上看这些人的资料；然后发现某个人经常和对方的首席财务官通信，于是请这个人帮我做引荐。我们显然不想这样做，因为这会打开所有人的邮件。

另一种做法是做一个工具。这个工具本身能查看公司里每个人的 Gmail，但它只返回关系强度分数。你把一个域名交给这个工具，并说明你在找首席财务官这类人。工具会查看公司里谁给这家公司发过邮件，排出分数，把分数返回给 agent。agent 拿到分数之后，再用 Slack 工具去联系分数最高的那个人，比如 Bob，对他说：我看到你和 Acme 的首席财务官 Jane 有联系。Bob 确认：是的。然后你的 AI 再问：我能不能起草一封介绍邮件，或者你能不能起草一封介绍邮件？Bob 同意，介绍完成，事情就做成了。

这是一种很好的做法。不知道你们有多少人在用。我们在 Town 对用户经常做的几类事情用了这种方法。我们会问自己：有没有一种保护隐私的工具，是我们所有用户都能接受其存在的？用户如果不想用可以退出。但这类工具有自然的网络效应，因为它能以一种受限制的方式穿过信息孤岛。

另一个有意思的例子是：允许公司里的其他人把邮件草稿放到你的收件箱里。你让同事以你的名义起草邮件，因为销售团队反正也会来找你要引荐，不如少点几下。

这里的问题是：在一家公司内部，人们是否接受你做出的隐私取舍？大多数时候可以。但这种做法仍然是手工的，也不是动态的。它是手工的，因为人类必须先想出这些工具，也许我能把这些工具做出来；它也是手工的，因为你必须向所有人解释这件事正在发生。如果人们不接受你做出的隐私与能力取舍，他们可能不喜欢这件事。而且，随着模型变强，这种做法本身并不会自动变得更好。这就是问题。

## 策略三：共享信息库，以及清扫 AI

第三种做法现在非常流行，但主要还出现在单用户场景里，也就是个人知识库。把它放到团队和公司层面，就变成一座共享信息库：你在公司内部、在公司的子群体内部，新建一个数据会持续积累的地方，并且随着时间往里面放入越来越多的内容。所有 agent 都能访问这些内容。这样一来，本来可以分享、却被卡在私有信息孤岛里的信息，会进入这个对全公司公开的空间。

一个例子是共享 skill。如果你在一个组织里写代码，代码仓库里很可能已经有共享 skill。任何人都可以改进它们。如果有人找到了更好的数据库性能分析方法，他可以写成 skill。下一次有人发现数据库查询很慢，就会用到这个性能分析 skill，于是每个人都成为更好的工程师。

另一个常见例子是：人们约定使用一些共享介质，比如 wiki、Airtable。他们形成一个习惯：随着时间往里面放入更多数据。这些做法是有效的，前提是你的 agent 拥有使用这些工具的能力，并且在行动轨迹上有足够的动力，把数据写入这些共享信息库，也从这些共享信息库里取数据。

我认为这种做法的下一个版本，是一些人已经在做的清扫 AI。如果这场演讲里有一个我认为特别有效的想法，就是清扫 AI。你在每一座私有信息孤岛里放一个 AI。这个 AI 有一份策略，说明哪些信息必须留在这座信息孤岛里；它也有一份关于全部共享空间的描述。一天结束时，它查看这座信息孤岛里的新信息，并把适合分享的内容放入对公司公开的空间。

这和你们已经在用的个人知识库是同一件事：一天结束时，AI 会帮你整理目标、朋友和其他个人事实。只不过现在这件事发生在公司层面。困难的部分是：如何挑选哪些私有信息可以分享，并放入共享信息库。我认为有两种做法。

第一种做法是询问人类。LLM 先列出准备贡献的内容，然后问用户：你是否接受我把这些内容放入共享空间？你读一遍，说可以。这会帮你省下很多时间，因为你本来就不会自己去做这件事。

第二种做法是让 LLM 执行一份策略。我认为事情会很快走到这里。未来六个月里，会有一批系统出现：公司把一份策略交给 LLM，信任它自动把本来会保持私有的信息，越来越多地放入对公司公开的空间。如果你在一家 Fortune 500 的大型企业，这件事短期内不会发生。但如果你看 10 人、50 人、高信任、误用数据概率低、而且很清楚哪些数据绝对不能分享——基本上就是财务数据和人力资源数据——的小公司，你会看到大量这种系统。它真正能改进的，是系统在日常共同工作上的行动轨迹。

## 策略四：把人类当作信息通道

第四种做法很明显：把人类当作信息通道。这就是传统的 agent-to-agent。我的 agent 问你的 agent：谁认识 Acme 公司财务团队的人？你作为人类看到这个请求，表示可以，于是允许它在我的邮件里查找信息。然后它把结果给你看。你再说：可以，把这个结果发给提问的人。

这种做法的大问题是：只要只有少数人真正拥有答案，你就会向所有人发送请求。如果我在一家 100 人的公司问这个问题，100 个人都会在 Slack 上收到通知，被要求批准这些请求，好让系统从他们的个人关系网里寻找这个问题的答案。这非常没有效率。

## 策略五：黑箱方法，只在分享这一步征求同意

因此有一个更好的版本。这个版本非常强，但我很少在实践里看到。它是黑箱方法。我希望我有一张图，可惜没有。

黑箱方法指的是：当你提出一个只能通过查看其他人信息孤岛才能回答的问题时，你使用一次 LLM 调用。没有人能访问这次调用的过程记录。这次调用获得全部数据的访问权限，并到达答案，或者到达它即将发起的那一次正确工具调用。然后它查看：做出这次工具调用需要哪些信息。它只向拥有这些信息的人征求批准，询问是否可以发起这次工具调用。

回到前面的例子。当我问公司里的 100 个人：你是否认识 Acme 的首席财务官？这个请求会发到公司里每个人的 agent。所有这些 agent 都会查看自己的 Gmail 和私有信息孤岛，确认自己是否和这位首席财务官有联系。这一步自动发生，没有任何人类被要求批准这次查找。然后，黑箱里的 agent 得到一份名单：20 个人有联系。它根据邮件往来判断谁的关系最强，判断出是 Bob。然后它只问 Bob：Jean-Denis 希望你把他介绍给 Acme 的首席财务官 Jane。我知道你和她关系很好。我是否可以把这一点分享给 Jean-Denis？你点一下可以。事情就完成了。

关键在于：你必须信任这个黑箱。你必须接受：为了一次没有人能查看过程记录的 LLM 调用，所有信息孤岛都可以被打开；在出现分享、或者出现那一次正确步骤之前，系统不必征求许可。

在一家公司内部，这件事并非做不到。安全团队和合规团队也可以接受它。你必须确保有人类参与的那一步是正确的，也必须确保在得到最后答复之前，没有其他信息被传出去。

这种做法的噩梦场景是：有人问你是否认识另一家公司的招聘人员，而按你的职责你本来不该和那家公司的招聘人员有联系。提问的人其实是想发现你正在别处面试。即使使用黑箱，你有时仍然会在无意中放出本不该放出的信息。你必须认真思考如何把系统设计好。

## 最快见效的方向，以及失败方式

以上就是这些做法。如果我要押注一个立刻能看到回报、而且会同时出现在开源的 Claude 类系统和小公司里的方向，那就是由 AI 自动维护的 wiki，也就是持续更新的信息库。我认为会出现数据库版本，也会出现 wiki 版本。我认为我们会越来越信任 LLM 来决定什么可以分享、什么不可以分享。

这里有问题。信息孤岛里的提示注入会是一个真实问题。如果一座信息孤岛更开放，有人往里面放入有害内容，然后 agentic search 把它取出来，坏事就会发生。

共享 wiki 也很容易完全偏离正确内容。LLM 一旦写错一条信息，这条错误信息就会长期留在那里，并持续影响后续检索。我有一份个人知识库，它现在仍然认为我的 agent 叫 Apex，但我一个月前已经把这个 agent 改名为 Ivy。在我的记忆库的某个地方，Apex 还在，我去不掉它。对 Apex 来说，这只是一件好笑的事。如果这是一条关于你业务的真正错误信息，事情会困难得多。

如果任何步骤都没有人类参与，就一定会出现错误的、不该发生的信息披露。有时一次错误披露会让人被解雇；有时一次错误披露完全没有影响；有时客户会起诉你。所以必须小心。

这些听起来都很好，但还要回答：谁批准什么、什么被记录、什么可以被撤销。黑箱这个想法很好，但它不能真正是黑箱。你们公司里总有人会在某个时刻要求审计它，想理解里面发生了什么。在某个层级上，必须有安全负责人或其他人能够访问全部数据。

## 前沿是自动执行，先划出低敏感区

我认为前沿是自动执行。写代码时，我们曾经批准所有事情；然后我们变成不管不顾、直接执行；现在 Anthropic 给了我们 auto mode。auto mode 会判断我们是不是正在做一件有点鲁莽的事，并提醒我们。

跨越信息孤岛的 agent-to-agent，也会走同一条路。我们会先接受：低敏感信息可以被取出，并放入公共空间。然后我们会保留一个区域：那里始终由人类审阅，或者始终由人类批准。随着时间推移，LLM 会更强，我们会更擅长把安全策略写进 LLM，也会更擅长为最困难的区域设计把隐私取舍做对的工具。建设共享信息库会越来越自动，有时连“要不要让人类参与”这件事也会越来越自动。

一个例子是：如果我要一份每周例会的笔记，这场例会是我们和某家供应商的财务团队开的，LLM 可能会判断：根据你的职责，我不需要向那些团队里的任何人征求许可，我可以直接把笔记分享给你。这样做可以。它可以查看内容，可以查看我的职责，可以从风险角度判断这次披露可以接受。

自动执行的好处是：如果你按这种方式设计系统，系统会随着模型能力一起增强。我的建议是：如果你已经有 agent-to-agent，或者更准确地说，已经有跨越信息孤岛的工作，一定要先定义一个低敏感区，并接受 LLM 在这个区域里自己做决定。先接受这件事。然后，随着时间推移，这个区域会变大，你的系统会自然变得更强。这就是你希望发生的事情。

## 网络效应，以及跨公司的未解问题

我还剩一分钟，这是结论。我们讲了五种做法：信任边界、定制工具、共享信息库、有人类参与的通道，以及黑箱版本。这些做法都很强。

在公司内部，我认为这些事情很快就能运行起来。比较有意思的问题是：我们在多大程度上接受一种围绕隐私的自动模式。我认为真正有意思、而我没有答案的问题是：你能不能想到一些场景，让多家公司同意，让一个共同的 agent 跨越它们各自的信息孤岛工作。谁做成这件事，会比我更有钱。

世界上有一家我不会点名的公司，在做金融相关的事情。它们和很多投资银行合作。对这些投资银行来说，为了贷款这类用途，分享关于未上市公司的私有数据是有收益的。它们已经开始朝这个方向看：信任彼此的 agent，让这些 agent 在过去本应保持私有的信息上工作，并由 agent 决定什么可以访问、什么不可以访问。这件事很有意思。我认为，一旦你找到一些跨公司的用例，那会是继续朝这个方向推进的很好起点。

不过，作为一个人，我会问自己：我是否信任一个由 agent 做出全部隐私决定的未来？我不确定。无论好坏，事情正在朝这个方向走。
